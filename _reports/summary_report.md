# 通用 CUA 能力评估报告：140 个开源方案，到底能替你做什么

> 数据日期：2026-11-07。评估对象：`F:\coding_cua` 清单内的 140 个公开 GitHub 仓库。本文所有名次、分数、档位数量均可在 `showcase\data\cua_rank.json` 与 `_reports\cua_top_list.md` 中逐条回溯。

**开头：三分钟看懂这份报告**。CUA 是「Computer Use Agent」的缩写，白话就是**让软件自己看屏幕、认按钮、动鼠标键盘**，把人在电脑上的重复操作替下来。它不是一个新硬件，而是一类程序：有的读系统控件，有的靠截图识别，有的直接在浏览器里执行，有的只是编排调度。

这份报告不再围绕某一个聊天工具转。它把全库 140 个方案放在同一把尺子上量：**先看真正能操作到什么程度，再看易用性、文档与维护、稳定性证据、平台广度，最后扣风险分**。同一路线内部可以直接比；跨路线时，差别写在每条方案的 `whyZh` 里，本文也会讲清取舍。

读法建议：先看第 3 节知道自己有多少选择，再看第 6 节的决策树对号入座，最后按第 7 节准备落地。不要从第 4 节的 Top 10 直接抄，名次高不等于适合你的任务。

## 一、CUA 能替你做什么，做不到什么

**能做的，是「有明确界面、有固定步骤、结果可核对」的活。**

| 能做的事 | 典型样子 | 为什么适合 |
|---|---|---|
| 批量录单 | 把 Excel 里的客户信息逐条填进业务系统 | 字段固定、重复度高、错了能查 |
| 跨系统搬数据 | 从后台导出报表，整理后导入另一个系统 | 步骤清晰、中间结果可保存 |
| 表格整理 | 多份报表合并、去重、按规则分类 | 规则可写成判断、便于复核 |
| 发票/单据处理 | 下载票据、识别关键字段、登记台账 | 单张任务短、失败可退回重做 |
| 网页后台操作 | 登录后台、查订单、改状态、发通知 | 浏览器自动化最成熟 |
| 桌面软件操作 | 老客户端里点菜单、填窗口、导出文件 | 无障碍树或视觉点击可做 |
| 固定流程回放 | 每天同一时间跑同一套点击 | RPA 的强项，成本最低 |
| 移动端重复操作 | 真机上点按、滑动、填表、截图 | 移动端有成熟驱动 |

**做不到的，必须提前说清。**

| 做不到的事 | 现实原因 |
|---|---|
| 替你做判断和担责 | 它只会执行，不会承担业务后果；审批、定价、承诺必须人来 |
| 稳定通过验证码与强风控 | 验证码、设备指纹、登录保护本身就是防自动化 |
| 操作自绘界面 | 游戏、部分客户端、画布类界面没有标准控件，只能靠视觉猜 |
| 长时间无人值守 | 弹窗、网络抖动、界面改版会累积误差，越长越容易断 |
| 高并发、7×24 | 大多数方案是单机单会话，不是服务端集群 |
| 绕过平台规则 | 破解协议、注入客户端属于外挂，法律与账号风险不可控 |
| 保证 100% 正确 | 没有方案给出可复核的业务成功率；必须设计人工复核与回滚 |

一句话：**CUA 适合「搬运、重复、可核对」，不适合「判断、承诺、不可逆」。**

## 二、五条技术路线的原理与代价

术语先解释：**API** 是软件官方开给外部程序的门；**SDK** 是配套的工具包；**无障碍树**是操作系统给每个按钮、输入框编的一份「户口册」，读它就能按名字找到控件；**坐标点击**是截屏后按像素位置点鼠标；**RPA** 是录制人的操作再回放。

| 路线 | 白话原理 | 最大优点 | 最大代价 | 代表项目 |
|---|---|---|---|---|
| 官方 API/SDK | 走官方开的门，按接口收发数据 | 合规、稳定、可审计 | 官方没开放的能力一概做不到 | wechatpy、PowerWeChat、appium |
| 无障碍树 | 读系统控件户口册，按名字点按钮 | 语义定位稳，界面小改不一定失效 | 应用不暴露控件就只剩空壳 | agent-desktop、xa11y、pywinauto |
| 屏幕视觉+坐标点击 | 截图给模型看，算出坐标再点 | 什么界面都能试，不依赖接口 | 会点偏，缩放、主题、动画都影响 | UI-TARS、Agent-S、OmniParser |
| 浏览器自动化 | 在浏览器里点击、填表、取数 | 最成熟、成本最低、调试方便 | 出了浏览器就没有抓手 | browser-use、nanobrowser |
| RPA/工作流 | 录制步骤，按流程回放与编排 | 可复用、可审计、非程序员能维护 | 界面一改就要改脚本 | astron-rpa、robotframework、TagUI |

另外两类要单独说：

- **Agent 框架**：它负责拆任务、排顺序、调工具，本身不一定长手长脚。适合做「大脑」，但最终操作要靠上面五条路线里的「手脚」。代表有 openinterpreter、magentic-ui、droidrun。
- **协议/注入（高危）**：破解通信协议，或把代码注入客户端进程。能力看着直接，代价是违反平台规则、可被永久封禁，甚至涉及法律与数据安全问题。全库 7 个此类项目全部评为「勿用」。

跨路线的取舍可以记成一句话：**要稳走官方接口或无障碍树，要通用走视觉，要快走浏览器，要便宜走 RPA；要「什么都能点」就得接受「什么时候点偏不知道」。**

## 五、「勿用」类型的后果

29 个「勿用」不是「不好用」，而是「用了可能出事」。主要分四类：

1. **协议破解与注入外挂（7 个路线标注为高危，另有若干账号风控类）**。后果：平台可永久封禁账号，涉及破解与数据解密时还有法律与隐私风险；客户端一升级就整体失效，投入打水漂。
2. **个人聊天工具的批量/定时外发**。后果：轻则限流、封功能，重则永久封号；群发还会波及客户关系，业务损失大于省下的人力。
3. **半年以上无提交、或作者已声明缺维护**。后果：新系统、新版本没人适配，出了问题只能自己修；这类项目即使当年很强，也不该作为长期基础设施。
4. **只有演示、没有真实系统验证的原型**。后果：演示能跑，真实环境一用就碎；没有失败恢复、没有权限控制、没有回归测试。

判断口径很简单：**只要一个方案需要你「绕过平台规则」或「承担封号/法律风险」，它的分数再高也不进入候选。**

## 六、怎么按自己的任务选（决策树）

先回答第一个问题：**任务发生在哪里？**

- **在网页后台里** → 走浏览器自动化。首选 browser-use；要更轻、装在浏览器里就用 nanobrowser；要隔离与批量抓取看 steel-browser。
- **在 Windows 桌面软件里** → 走无障碍树。会写 Python 选 pywinauto 或 Python-UIAutomation；要接编码代理选 Hybrid-Computer-Use、dsh-computer-use-win；老系统没有控件再补视觉。
- **在 macOS 桌面软件里** → 选 agent-desktop 或 xa11y；要配方复用看 ghost-os；只做固定表单填写可看 FluidUse。
- **在 Linux 桌面里** → computer-use-linux（Wayland 可用）；文本与控件混合看 epistex computer-use。
- **在手机 App 里** → 测试与批量选 appium；自然语言任务选 droidrun；安卓设备集群选 lamda。
- **在表格、单据、邮件、文件里** → 走 RPA/工作流。astron-rpa 组件最齐；TagUI 语法最简单但上游已停更；A9T9 适合老系统回放。
- **流程固定、每天同一时间跑** → RPA 优先，成本最低、责任最清楚。
- **流程经常变、需要临场判断** → Agent 框架加一条执行层；先小范围试，不要直接接管关键业务。
- **只是要「看懂界面」** → 屏幕解析模型，如 OmniParser；它只负责看与指，点击要另配执行层。

第二个问题：**能不能拿到官方接口？** 能，就优先官方 API/SDK；不能，再考虑无障碍树；两者都不行，才用视觉。

第三个问题：**错了能不能撤回？** 不能撤回的操作（付款、删除、对外发送、改合同）必须加人工确认，不管用哪条路线。

第四个问题：**有没有人维护？** 没有维护人，就不要选需要跟着客户端升级的项目；宁可缩小范围，用最笨但稳定的方式。

## 七、落地前要准备的 9 件事

1. **把任务写成边界**：做什么、不做什么、哪些动作必须人工确认。写不清楚，后面一定返工。
2. **拿到账号与最小权限**：只给完成任务需要的权限；能只读就先只读。权限由业务负责人和系统管理员共同确认。
3. **准备独立测试环境**：测试账号、测试数据、测试设备。不要在生产账号上试点击。
4. **选一条主路线加一个备选**：主路线负责 80% 的稳定流程，备选用于主路线失效时兜底。
5. **先做「只观察不操作」的干跑**：让它截图、识别、给出计划，但不点。确认它看对了再放开手。
6. **打开全程记录**：每一步截图、动作、耗时、结果都留痕；没有记录就无法定位失败。
7. **设置人工确认点**：对外发送、删除、付款、改状态这类动作前必须停一下等人。
8. **做 20 次小样本试跑**：覆盖正常、异常、弹窗、网络慢、界面改版五类情况，记录失败类型而不是只看成功数。
9. **安排维护人与回归周期**：指定谁负责，客户端或系统升级后跑一遍固定用例；没有维护人就不要上线。

前 3 件决定「能不能开始」，中间 3 件决定「敢不敢放手」，后 3 件决定「能不能长期活」。

## 八、成功率与维护成本的真相

**先说成功率：没有。** 这 140 个仓库里，没有一个给出可复核的业务成功率；少数项目给出的「约五成」是公开基准任务上的模型分数，不等于你的业务成功率。本报告不编任何百分比。

能确定的是三件事：

- **任务越短、界面越标准、结果越可核对，成功率越高**；反过来，长流程、自绘界面、强风控，失败率一定上升。
- **基准分数不能外推**。评测环境是固定的，你的客户端版本、分辨率、网络、账号状态都在变。
- **成功率的正确用法是「自己测」**：同一任务跑 20 次，记录成功、点错、卡住、结果错四类，再决定是否扩大范围。

**维护成本的真相**：CUA 不是装一次就完。客户端升级、驱动升级、模型换版本、网页改版，都会让原本能跑的流程失效。现实做法是：固定版本、锁驱动、准备好回归用例、每月至少跑一次。把它当成一条需要保养的生产线，而不是一个买回来就能用的软件。

**举例（不是本报告主线）**：某保险销售想让程序处理企业微信的外部客户消息。即使选最合规的官方接口方案，也只能触达成员确认过的会话，外部群没有开放接口；界面自动化看似能补，但属于非官方接入，账号风险要自己承担。这个例子说明的是同一个道理：**合规方案买到的是「稳定」，不是「全自动」；想要全自动，往往就要越过规则，而越过规则的代价不该由业务承担。**
