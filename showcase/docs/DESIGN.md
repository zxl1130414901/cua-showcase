# 设计说明

## 1. 目标与读者

读者是不写代码、但要判断「该用哪套自动化方案」的人：关心「能不能操作我这个软件」「要花多少精力」「会不会被封号」，而不是 GitHub 星标。

所以站点不是「项目导航」，而是**选型决策工具**：

- 第一屏先给通用结论：CUA 没有万能选手，先按「要操作什么」分流；
- 任何排序、标签、风险判断都能追溯到本地报告或明确口径；
- 专业术语首次出现时给一句人话解释；
- 风险用「颜色 + 文字 + 符号」三重表达，色盲或黑白打印也能读懂。

企业微信不再是主轴，只作为「官方接口 + 人工确认」的真实案例出现在技术路线页，以及详情页折叠的历史示例里。

## 2. 信息架构

```
#/            决策页：通用结论 → 三条硬事实 → 七个用途入口 → Top10 → 对比入口
#/all         完整清单：自然语言搜索 / 5 组筛选（类型、平台、等级、路线、通用维度）/ 6 种排序 / 勾选对比
#/repo/<id>   项目详情：13 个分区（定位 … 最适合的场景 / 谁不该用 … 和谁比怎么选）
#/compare     对比：2–4 个项目，逐行差异高亮
#/routes      技术路线：5 条路线的原理、适合谁、开发量、稳定性、风险、代表项目，以及企业微信案例
#/method      口径页：综合分公式、六维评分、等级与路线、数据来源与局限、搜索口径、术语表
```

旧链接 `#/wecom` 会重定向到 `#/routes`，避免历史书签失效。

首页顺序是刻意设计的漏斗：

1. **通用结论**：一句话「CUA 没有万能选手，先按要操作什么分流」，先阻止读者从 140 个项目里盲试。
2. **用途入口**：七个入口（浏览器 / Windows / macOS / 手机 App / Office 文档 / 批量流程 / Agent 框架）首屏可见，点进去自动带上对应筛选。
3. **三条硬事实**：截图点击类看不懂界面语义、浏览器与桌面是两套技术、成功率高度依赖目标软件是否改版；每条注明来自 `summary_report.md` 的哪一节。
4. **Top10 与搜索**：直接读 `cua_rank.json` 的 rank 1–10，卡片写明名次、综合分、一条能力描述与最大风险。
5. **对比入口**：给仍拿不准的人一个低成本的下一步。

## 3. 首页为什么这样排

- **先分流而不是先排名**：项目排名只在「同一路线内」有意义；路线选错，名次再高也用不上。用途入口因此放在 Top10 之前。
- **用途入口给数量**：每个入口标注该路线/平台下有多少项目，避免点进去发现是空的。
- **Top10 卡片必须带风险**：只写优点会把「能用」误读成「可上线」，每张卡片都保留一条 `riskZh`。
- **首屏实测**：1440×900 与 375×812 下，结论、七个用途入口均可见；移动端三条硬事实需要轻微滚动，这是刻意的取舍（不压缩字号）。

## 4. 综合分与推荐等级

`cua_rank.json` 是评分的主来源：构建时把 `rank / score / tier / primaryRoute / capabilityZh / bestForZh / whyZh / riskZh / subScores` 合并进每条项目。页面与排序直接使用文件里的 `score`，本地公式只在该文件缺失时兜底。

本地兜底公式（0–100）：

```
综合分 = 覆盖 35 + 易用 25 + 文档 15 + 维护 15 + 稳定 10 − 风险扣分(≤15)
```

| 分项 | 上限 | 计算 |
| --- | --- | --- |
| 覆盖 | 35 | coverage（0–10）× 3.5 |
| 易用 | 25 | usability × 2.5 |
| 文档 | 15 | docs × 1.5 |
| 维护 | 15 | maintenance × 1.5 |
| 稳定 | 10 | stability × 1.0 |
| 风险 | −15 | 含 hook / 注入 / 破解 / 多开等关键词 −10；RPA 工具 −2；最多扣 15 |

最终 `clamp(0, 100)`，保留 1 位小数。档案未整理时，各维保守取 4 分，不把「不知道」当成优秀，并在页面标注「估算」。

推荐等级四档（来自排名文件）：

| 等级 | 含义 |
| --- | --- |
| 推荐 | 路线正确、能力与维护都到位，值得优先评估 |
| 可用 | 能解决问题，但有平台、成本或维护上的明确限制 |
| 谨慎 | 能力有限或风险较高，只在特定条件下考虑 |
| 勿用 | 不建议用于生产：协议破解、停止维护、或边界与宣传严重不符 |

「勿用」在清单、详情与筛选项里都附带「（有封禁风险）」文字，避免读者把「推荐」误读成「安全」。

## 5. 六维评分

`subScores` 均为 0–100（按 10 分制展示时除以 10），由研究报告给出：

| 维度 | 含义 |
| --- | --- |
| coverage | 能覆盖多少目标场景与应用 |
| usability | 从零到跑起来的门槛 |
| docs | 文档完整度与示例可照抄程度 |
| maintenance | 更新频率与 Issue 响应 |
| stability | 目标软件改版后还能不能跑 |
| breadth | 是否跨平台、跨软件，还是只服务单一产品 |
| riskPenalty | 风险扣分 |

详情页把这六维画成条形图，并单列风险扣分；清单页只展示综合分与等级，避免信息过载。

## 6. 筛选、排序与自然语言搜索

- 默认按综合分（score）降序；同分按 rank 升序，再按星标降序、名称升序，保证结果稳定。
- 支持排序：综合分、星标、最近更新、类型、平台、名称；升降序可切换。
- 筛选组：类型、平台、推荐等级、技术路线、通用维度（需 GPU / 需付费 API / 中文友好）；**组间「且」，组内「或」**。
- 自然语言搜索：先去掉「我想 / 我要 / 帮我 / 怎么 / 如何 / 可以」等口语词，再按「并 / 然后 / 再 / 以及 / 和」拆成必须同时命中的片段；每个片段若未直接命中，会按同义词扩展（填表 → 表单 / 填写 / 录入；手机 → Android / iOS；文档 → Excel / Word / PDF 等）。
- 搜索范围：项目名、中文定位、中文总结、能做什么、技术方案、`capabilityZh`、`bestForZh`、`whyZh`、原始简介、标签、应用、平台与场景。
- 详情页头部显示「全库排名 第 N 名 / 140 · 综合分」；正文「最适合的场景 / 谁不该用」再次给出位置与六维分。
- 详情页 `stepsZh`、`successRateZh`、`appsZh` 完整展示，不做行数或字符截断。
- 对比最多 4 个；差异判定为「该维度文本不完全一致」，行首显示「差异」文字标记，不只靠底色。

## 7. 技术路线页

五条主路线：官方 API/SDK、无障碍树（UI Automation）、屏幕视觉 + 坐标点击、浏览器自动化、RPA/工作流；另有三类补充：Agent 框架、协议/注入（高危）、其他。

每一行包含：白话原理、适合谁、开发量、稳定性、主要风险与代价、项目数与均分、代表项目（可点击进详情）。项目数与均分由 `cua_rank.json` 的 `primaryRoute` 聚合计算，路线文案取自 `summary_report.md` 第二节。

页面最后保留「真实案例：企业微信外部消息」一节，用来说明「官方接口 + 本人确认」长什么样；该节不参与任何评分。

## 8. 数据合并与容错

`scripts/build-data.mjs`：

1. 读取 `manifest.json`（只读），以 140 条为基础；
2. 扫描 `data/details/*.json`，按 `id` 与 `owner__repo` 双键关联，单个文件解析失败只跳过并打日志；
3. 读取 `cua_rank.json`，按 id 合并排名字段；缺失时保留本地算法结果；
4. 字段全部做类型收敛：数组、字符串、0–10 分归一化；`scores` 缺失记为 `null`；
5. 缺档案：`hasDetail:false`，详情页显示「档案整理中」+ manifest 基础信息，列表照常显示；
6. 解析 `summary_report.md` 与 `wecom_research.md`：标题定位、表格转对象、链接提取；解析失败时有兜底文案；
7. 输出 `src/data/generated.json`，构建前自动执行。

全程只读上游，产物仅写 `showcase/` 内。

## 9. 单文件离线打包

- Vite 输出 `format: 'iife'` + `inlineDynamicImports`，避免 ESM；
- `cssCodeSplit: false`，CSS 单文件；
- `scripts/inline-html.mjs` 把 CSS / JS 内联，**并把 `<script>` 移到 `</body>` 前**：去掉 `type="module"` 后脚本不再延迟执行，留在 `<head>` 会在 `#root` 出现前运行；
- 内联时转义 `</script>`，避免提前闭合；
- 构建后硬校验 `type="module"` / `crossorigin` / `import.meta` / 外部脚本与样式表，任一存在即构建失败；
- 数据以 JSON 形式打包进 JS，`file://` 下无 fetch、无跨域问题。

代价是 `dist/index.html` 约 1224 KB（140 条原始字段 + 140 份中文档案 + 全量排名与报告），换来双击即用。

## 10. 视觉与无障碍

- **基调**：纸张暖白 + 深海军蓝 + 陶土色强调，介于「研究报告」与正式文件之间，避免 SaaS 仪表盘的冷感。
- **字体**：标题宋体（Source Han Serif / Songti SC / SimSun 回退），正文苹方/微软雅黑；不加载外部字体。
- **风险编码**：色块 + `✓ / ! / ×` 符号 + 文字评级，并在 `sr-only` 中重复语义。
- **等级编码**：tier 徽章同时给出图标与中文；「勿用」额外附文字警示。
- **键盘**：跳过导航链接、所有筛选为原生按钮（`aria-pressed`）、复选框有 `aria-label`、表格有 `caption`、章节标题有 `id` 关联。
- **窄屏**：表格在容器内横向滚动，页面本身不产生横向溢出；对比表首列粘性；导航横向滚动但 375px 下五项完整可见。
- **减弱动效**：遵循 `prefers-reduced-motion`。

## 11. 验证

`scripts/verify.mjs` 用 Playwright + 系统 Edge 打开 `file://` 产物，检查：

- 四档宽度（375 / 768 / 1024 / 1440）× 六个页面（24 组）无横向溢出；
- 首页首屏结论在前，七个用途入口在首屏内；
- 首页 Top10 与 `cua_rank.json` 的 rank 1–10 逐条一致（比对卡片链接）；
- `rankCount = 140`，四档数量为推荐 5 / 可用 45 / 谨慎 61 / 勿用 29；
- 清单 140 行、默认按综合分排序（首行为 rank 1）、tier 徽章 140 个、勿用 29 行且带文字警示；
- 自然语言搜索「我想自动填表并提交」有命中；
- 详情页 13 个分区、`#fit` 存在、无 `#wecom` 分区；`stepsZh` 条数与 `successRateZh` 字符数与档案完全一致；历史案例折叠默认关闭；
- 技术路线页 5 行路线、3 类补充、9 条决策与 4 条档位含义；`#/wecom` 重定向为 `#/routes`；
- 页面无「适配度」等旧口径残留；
- 首次 Tab 聚焦「跳到主要内容」；
- 控制台错误与页面异常计数（当前均为 0）；
- 输出 `shots/` 截图。

## 12. 已知取舍

- 不做后端、不做实时抓取：数据快照与档案补写都靠重新构建。
- 不展示「成功率」数字：没有可信公开数据，宁缺毋滥，档案里的说法原样展示并注明来源。
- 首屏事实卡在 375px 下需要轻微滚动才能看全三条；优先保证「结论 + 用途入口」，而不是压缩字号。
- 类型标签 `wechat-specific` 保留英文原值，筛选项显示「微信专用」。
- `needGpu` / `needPaidApi` / `chineseFriendly` 为关键词估算，可能漏判。
- tier 与 primaryRoute 是研究结论，不是官方认证；页面只承诺「可追溯」，不承诺「零风险」。
